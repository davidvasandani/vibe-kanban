<Note>
This page covers configuring MCP servers **within** Vibe Kanban for your coding agents. For connecting external MCP clients to Vibe Kanban's MCP server, see the [Vibe Kanban MCP Server](/integrations/vibe-kanban-mcp-server) guide.
</Note>

## Overview

MCP servers provide additional functionality to coding agents through standardized protocols. You can define a logical MCP server once in Vibe Kanban and assign it to one or more compatible coding agents.

## Accessing MCP Server Configuration

1. Navigate to **Settings** in the Vibe Kanban interface
2. Click on **MCP Servers** in the settings sidebar
3. Add or edit a logical MCP server
4. Select the compatible coding agents that should receive that server

## Popular MCP Servers

Vibe Kanban provides popular MCP server templates. Add a template, then choose the compatible agents that should receive it.

You can add the same template more than once. The first instance takes the template's own name; later ones are numbered (`gmail`, `gmail_2`, `gmail_3`), and you can rename each to something meaningful. This is how you run one connector against several accounts — two Slack workspaces, or a Gmail server per mailbox.

### Slack connector

The generic Slack template installs a pinned build of the
[davidvasandani/slack-mcp-server](https://github.com/davidvasandani/slack-mcp-server)
fork rather than the upstream npm package, because the fork adds attachment
retrieval:

```json
{
  "command": "npx",
  "args": [
    "-y",
    "https://github.com/davidvasandani/slack-mcp-server/releases/download/v1.3.0-vk.2/slack-mcp-server-vk-1.3.0-vk.2.tgz",
    "--transport",
    "stdio"
  ],
  "env": { "SLACK_MCP_XOXP_TOKEN": "YOUR_TOKEN" }
}
```

Release **v1.3.0-vk.2** is based on upstream 1.3.0 and includes fork commit
`04633fb892dc6dd38c3faffe29ff9b30829560c6`. The tarball is a launcher: it
downloads the server binary for your platform from that same release, verifies
it against a SHA-256 recorded at build time, caches it, and runs it. A
verification failure is fatal — the connector never falls back to a different
build. Paste your Slack user token (`xoxp-…`) in place of `YOUR_TOKEN` when
using this local stdio form.

Clustered self-hosted deployments can instead set
`VIBE_KANBAN_SLACK_MCP_URL` to one operator-hosted Streamable HTTP endpoint.
When set, Vibe Kanban exposes the bundled Slack definition as URL-only HTTP:

```json
{
  "type": "http",
  "url": "http://172.16.100.102:13080/mcp"
}
```

The Slack token then belongs only to the supervised server and is not written
to agent configuration. Exact saved copies of the previously shipped stdio
templates reconcile to this HTTP definition; modified or custom `slack` entries
are left untouched. Migration deliberately drops the old
`SLACK_MCP_XOXP_TOKEN` instead of turning it into a client header.

For generic stdio installs, the launcher verifies the platform binary, but npm downloads the launcher
tarball itself without an expected integrity value. A release writer could
replace that outer asset under the existing tag before the daily audit detects
it. Vibe Kanban records the expected launcher digest, audits it daily, and opens
a GitHub issue on failure; this is a detection control, not install-time
verification. Upgrades still use reviewed new `-vk.<n+1>` tags rather than
re-uploading an existing asset.

An operator-hosted Nix deployment can close that outer gap by fetching the
launcher tarball as a fixed-output derivation before passing the verified local
path to `npx`. The server still uses the same fork tag and platform-binary
digest checks.

<Note>
The fork exposes `attachment_get_data`, which takes a `file_id` (the ID shown in
a message's `AttachmentIDs` metadata) and returns that attachment's metadata and
content, up to 5 MB, using your connected Slack identity — Slack still enforces
channel and file permissions. It is enabled by default. To turn it off, set
`SLACK_MCP_ENABLED_TOOLS` to a comma-separated list of the tools you want and
omit `attachment_get_data`.
</Note>

Two launcher-specific environment variables are available for constrained
hosts:

| Variable | Effect |
| --- | --- |
| `SLACK_MCP_SERVER_VK_BINARY` | Runs the binary at this path and skips the download and checksum check. Use it on offline or air-gapped machines, or to test a local build. |
| `SLACK_MCP_SERVER_VK_CACHE_DIR` | Overrides the cache root (default: `%LOCALAPPDATA%` on Windows, otherwise `$XDG_CACHE_HOME` or `~/.cache`). |

#### Updating to a newer fork release

Fork releases are tagged `v<upstream-base>-vk.<n>` and their assets are
immutable — a correction ships as `-vk.<n+1>`, never as a re-upload. Renovate
opens a `needs-review` pull request when a new release appears. To adopt one:

<Steps>
<Step title="Cut the fork release">
In the fork, tag the revision and run `scripts/build-release.sh`, then publish
the binaries, the launcher tarball, and `checksums.txt` as release assets.
</Step>
<Step title="Update the pin">
Change the URL in `crates/executors/default_mcp.json`, any deployment-owned
fixed-output URL/hash, and the
`SLACK_MCP_FORK_TAG` and `SLACK_MCP_LAUNCHER_SHA256` constants in
`crates/executors/src/mcp_config.rs`, and the version named on this page — all
in the same change.
</Step>
<Step title="Verify the published artifact">
Run `cargo test -p executors slack_pinned_launcher_matches_recorded_digest -- --ignored`
to confirm the published tarball matches the recorded audit digest. `npx` does
not enforce this digest when it installs a URL package.
</Step>
</Steps>

### Gmail connector

The Gmail template installs a pinned revision of the
[davidvasandani/Gmail-MCP-Server](https://github.com/davidvasandani/Gmail-MCP-Server)
fork:

```json
{
  "command": "npx",
  "args": [
    "-y",
    "github:davidvasandani/Gmail-MCP-Server#030da3492753222a41645a9f343466d151c63f3c",
    "--tool-prefix=YOUR_PREFIX_"
  ],
  "env": { "GMAIL_CREDENTIALS_PATH": "/absolute/path/to/credentials.json" }
}
```

The pin is a commit SHA, so the installed code cannot change under you. Replace
both placeholders before saving — Vibe Kanban does not check that you have.

<Warning>
Give `GMAIL_CREDENTIALS_PATH` an **absolute** path. This value is copied verbatim
into your agent's configuration and the server is started without a shell, so
`~` is never expanded: a `~/.gmail-mcp/…` value resolves against the agent's
working directory, which is a task worktree. You would get a literal `~`
directory inside your repository — containing a Gmail refresh token.

Keep the trailing underscore on the prefix (`personal_`, not `personal`), or your
tools come out as `personalsearch_emails`.
</Warning>

<Note>
This entry installs from a Git revision rather than a published package, so `git`
and network access are required, and the **first** launch compiles the server
from source (roughly a minute). Later launches reuse the npm cache. Unlike other
connectors, no credential is stored in your agent's configuration — only the
*path* to a credentials file that the Gmail server owns.
</Note>

#### Prerequisites

Setting up Gmail is two steps, and both matter. Missing the first is loud;
missing the second is quiet.

<Steps>
<Step title="Create a Google Cloud OAuth client (once)">
Create an OAuth client of type **Desktop app** in a Google Cloud project with the
Gmail API enabled, download its JSON, and save it as
`~/.gmail-mcp/gcp-oauth.keys.json`.

This file identifies the *project*, not a mailbox, so every Gmail instance you
create shares it. That is why the template does not ask you for its path.

<Warning>
Without this file the server exits before it finishes starting, so **Test
connection** reports a failure naming the missing file. That is unfinished setup,
not a broken connector.
</Warning>
</Step>

<Step title="Authorise each mailbox (once per account)">
Run the server's own `auth` command in a terminal, once per mailbox, with
`GMAIL_CREDENTIALS_PATH` pointing at where that account's tokens should live.
Omit `--tool-prefix`; it plays no part in authentication.

```bash
GMAIL_CREDENTIALS_PATH=~/.gmail-mcp/credentials-personal.json \
  npx -y github:davidvasandani/Gmail-MCP-Server#030da3492753222a41645a9f343466d151c63f3c auth
```

Your browser opens for consent, and the refresh token is written to that path.
Repeat for each mailbox with a different filename.

Narrow the permissions you grant with `--scopes`, for example
`--scopes=gmail.readonly`. Deleting messages requires the full scope.

<Warning>
Skipping this step for an account is the quiet failure: the connector still
**tests green**, because listing tools needs only the OAuth client file. It fails
the first time the agent actually reads mail.
</Warning>
</Step>
</Steps>

#### Running several mailboxes at once

One server instance serves exactly one mailbox, because it loads a single set of
credentials. For several mailboxes, add the Gmail template once per account and
give each instance its own credentials path and its own tool prefix:

| Server name | `GMAIL_CREDENTIALS_PATH` | `--tool-prefix` |
| --- | --- | --- |
| `gmail_personal` | `/home/you/.gmail-mcp/credentials-personal.json` | `personal_` |
| `gmail_work` | `/home/you/.gmail-mcp/credentials-work.json` | `work_` |
| `gmail_client` | `/home/you/.gmail-mcp/credentials-client.json` | `client_` |

Substitute your own home directory. These must be absolute for the reason given
above; the `~` in the `auth` command below is expanded by your shell, but the
same text in the configuration field is not.

Server names are protocol identifiers, so they may contain only letters, digits,
underscores and hyphens — `gmail_personal`, not `Gmail (Personal)`.

<Warning>
Give every instance a **different** `--tool-prefix`. Some agents identify tools
by their base name across servers, so two instances sharing a prefix leave one
silently shadowing the other: you see a working `search_emails` that reads the
wrong mailbox. With distinct prefixes the agent sees `personal_search_emails` and
`work_search_emails` and can address each mailbox deliberately.

Two instances sharing a `GMAIL_CREDENTIALS_PATH` simply read the same mailbox.
</Warning>

Each instance contributes 28 tools, so three mailboxes add 84. Assign only the
instances an agent genuinely needs, and use `--scopes` to keep each one narrow —
see the tip on limiting MCP servers below.

#### Updating the pin

Renovate cannot track a commit SHA on a fork that publishes no releases, so this
pin is updated by hand. A bump moves the SHA in
`crates/executors/default_mcp.json`, the `GMAIL_MCP_FORK_REVISION` constant in
`crates/executors/src/mcp_config.rs`, and the revision on this page — together.

There is no separate checksum to refresh and no scheduled audit, unlike the Slack
connector above: a commit SHA cannot be re-pointed, so a recorded digest would
only ever confirm that a hash equals itself. Note that the SHA pins the fork's
source, not its dependency versions — installing from Git runs the package's own
build, which resolves its dependencies from npm at that moment.

### Brink POS connector

The Brink POS template runs the `brink-pos-mcp-server` package over stdio. It is
a SOAP client for [Brink POS](https://github.com/davidvasandani/mcp-brink) that
lets an agent place test orders, read order details and status, test OLO
(online-ordering) connectivity, and read a register's current business date:

```json
{
  "command": "npx",
  "args": ["-y", "brink-pos-mcp-server"],
  "env": {
    "BRINK_ACCESS_TOKEN": "YOUR_TOKEN",
    "BRINK_LOCATION_TOKEN": "YOUR_TOKEN"
  }
}
```

Replace both placeholders before saving — Vibe Kanban does not check that you
have. `BRINK_ACCESS_TOKEN` is required. `BRINK_LOCATION_TOKEN` is the default
register for the connection; tools that accept a `location_token` argument can
override it per request, so you can point one instance at several locations.

<Warning>
`BRINK_LOCATION_TOKEN` is a Base64 value and must keep its `==` padding. A token
copied without it — for example `EXAMPLE_LOCATION_TOKEN` — fails authentication;
restore the trailing `==` so it ends `EXAMPLE_LOCATION_TOKEN==`.
</Warning>

<Note>
The server defaults to the Brink production API
(`https://api13.brinkpos.net/Ordering.svc`). To target a different endpoint, add
an optional `BRINK_API_URL` entry to `env`.
</Note>

Unlike the Slack and Gmail templates, this entry is an unpinned package launch,
so `npx` must be able to resolve `brink-pos-mcp-server` on the agent host —
publish it to the npm registry your deployment uses (public npm or a configured
private registry) before adding the server.

## Adding Custom MCP Servers

You can also add your own MCP servers by configuring them manually:

<Steps>
<Step title="Create the logical server">
Click **Add server**, enter the server name, and choose the transport configuration.
</Step>

<Step title="Choose assignments">
Select one or more compatible agents. Vibe Kanban writes the server into each selected agent's native MCP configuration file.

Example stdio server:
```json
{
  "command": "node",
  "args": ["/path/to/my-server.js"]
}
```
</Step>

<Step title="Save and Test">
After updating the JSON configuration:

1. Click **Save** to apply changes
2. Click **Test connection** to test saved native entries
3. Review test results per server and per assigned agent

<Check>
These changes update the global configuration file for each assigned coding agent and persist even if you stop using Vibe Kanban.
</Check>
</Step>
</Steps>

## Conflicts and compatibility

## Shared authentication gateway

For an OAuth-protected HTTP MCP server, run **Test connection** and choose
**Connect** when authentication is required. Vibe Kanban completes OAuth once,
encrypts the upstream access and refresh tokens locally, and writes a protected
loopback gateway URL to every matching assigned agent. Upstream credentials are
never copied into agent-native configuration.

Use the authentication badge to distinguish shared gateway, agent-native,
explicit-header, and unauthenticated modes. **Reconnect** rotates the shared
connection; **Disconnect** makes it unavailable to all assignments. Removing a
single assignment leaves remaining assignments connected. Test results report
the gateway and upstream boundaries separately.

For a server behind Cloudflare Access, an interactive HTTP redirect during OAuth
discovery produces service-token guidance. The optional Access client ID and
secret are write-only and centrally encrypted.

If Vibe Kanban finds same-name native entries with different definitions, it shows
a conflict instead of choosing one silently. Rename or delete one of the entries
before saving shared changes.

Some agents support fewer MCP transports than others. Vibe Kanban blocks an
assignment when the transport cannot be represented safely in that agent's
native configuration.

## Best Practices

<Tip>
**Server Selection**: Choose MCP servers that complement your coding agent's primary function. For example, use Playwright for agents focused on web development.
</Tip>

<Tip>
**Limit MCP Servers**: Avoid adding too many MCP servers to a single coding agent. Too many servers and tools will degrade the effectiveness of coding agents by overwhelming them with options.
</Tip>

## Refresh tools in an active workspace

After you enable an MCP server or update its tools, select **Restart agent for
MCP changes** in the session toolbar. Vibe Kanban starts a fresh agent process
with the latest MCP configuration while keeping the same workspace and
conversation.

If a turn is running, Vibe Kanban asks for confirmation and lets that turn
finish before it starts the new process. The restart does not change the tool
schema of a model request that is already in progress.

<Info>
The connection test in MCP settings reads the server's current inventory, but it
does not update an agent process that is already running. Use the session
toolbar action to adopt the tested inventory.
</Info>

Codex also supports an internal live-refresh operation used by MCP callers. It
queues the new configuration for the next active turn, so the initial result is
**Pending next turn** rather than success. After that turn starts, Vibe Kanban
reads the thread-scoped Codex MCP status and records the sorted tool names and a
schema fingerprint as well as the tool count. This distinguishes tool additions,
removals, and schema-only changes.

Other executors report **Unsupported** for this internal operation when they do
not expose a live, confirmable MCP reload. Vibe Kanban does not substitute the
independent connection test for live adoption; use the agent restart instead.

Codex publishes a complete MCP runtime at the next-turn boundary. This makes
publication atomic and does not interrupt the current turn. The pinned status
protocol does not report whether an individual server was restarted or reused,
so Vibe Kanban shows that field as unknown. It also cannot retain an old working
connection for only one server when that server's replacement fails; the result
reports that limitation instead of claiming the old tool remains callable.

Refresh diagnostics identify servers only by configured name and use
allow-listed remediation. Environment values, tokens, OAuth material,
authenticated URLs, and raw subprocess output are not returned.

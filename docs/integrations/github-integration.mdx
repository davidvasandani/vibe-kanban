---
title: "GitHub Integration"
description: "Connect to GitHub to create pull requests and manage your workflow directly from Vibe Kanban"
---

Vibe Kanban integrates with GitHub to let you create pull requests directly from your task attempts. This integration relies on the [GitHub CLI (`gh`)](https://cli.github.com/) being installed and authenticated on your system.

## Setup

There is no need to configure GitHub in the Vibe Kanban settings manually. The integration is designed to work out-of-the-box if you have the GitHub CLI installed.

### Automatic Setup
When you attempt to create your first Pull Request, Vibe Kanban will check if the GitHub CLI is available. If it's not found or not authenticated, you will be guided through the setup process:

1.  **On macOS**: You will see a dialog offering to install the GitHub CLI via Homebrew automatically.
2.  **On Windows/Linux**: You will be provided with instructions to install the CLI manually.

### Manual Setup
You can also set up the integration manually in your terminal before using Vibe Kanban:

1.  **Install GitHub CLI**: Follow the [official installation instructions](https://github.com/cli/cli#installation) for your operating system.
2.  **Authenticate**: Run the following command in your terminal and follow the prompts:
    ```bash
    gh auth login
    ```
    Select **GitHub.com**, choose **HTTPS** or **SSH** as your preferred protocol, and complete the login via the web browser.

## Creating a Pull Request

Once the GitHub CLI is ready, you can create pull requests directly from a task:

1.  Open a task that has changes you want to merge.
2.  Click the **Create PR** button.
3.  A dialog will appear pre-filled with:
    *   **Title**: Derived from the task title.
    *   **Description**: Derived from the task description.
    *   **Base Branch**: The target branch for your changes (defaults to the repository's default branch or the one specified in the attempt).
4.  Click **Create** to open the PR on GitHub.

If the operation is successful, the task status will update, and a link to the new Pull Request will be available.

## GitHub App organisation credentials

In **Settings → Repositories → GitHub organization tokens**, you can select
**GitHub App installation** instead of a personal access token. Existing PAT
entries continue to work. An App installation lets the PR tools read check runs
posted by other Apps, subject to repository access.

1. Create a GitHub App in your organisation's developer settings. You do not need
   a webhook for Vibe Kanban's credential flow.
2. Grant these repository permissions, then install the App on only the
   repositories that Vibe Kanban manages:

   | Permission | Access |
   | --- | --- |
   | Metadata | Read |
   | Contents | Read and write |
   | Pull requests | Read and write |
   | Checks | Read |
   | Commit statuses | Read |
   | Actions | Read |
   | Workflows | Write, only for pushing `.github/workflows` changes |

3. Generate an RSA private key. Store the complete multiline PEM in a 1Password
   field that the coordinator's configured 1Password credential can read. Copy
   the field's `op://vault/item/field` reference. Do not paste the PEM into Settings.
4. Add or edit the organisation entry. Choose **GitHub App installation** and
   enter the App ID, installation ID and private-key reference. The installation
   must belong to the configured GitHub owner and App.
5. Select **Check credential health**. Confirm that the App is reachable, the
   installation is found, a token is minted and required permissions are present.
6. Start a new workspace session after changing credentials. Server PR and git
   operations use the updated entry on their next request.

Vibe Kanban signs App JWTs on the coordinator and caches installation tokens
until five minutes before GitHub's returned expiry. Workspace `gh` and git
commands request a current token when they run. They receive an opaque refresh
capability, never the App private key. Capabilities expire after seven days;
start a new session to renew them. Editing or deleting the credential revokes
existing capabilities. Workspace commands require `curl` for command-time
refresh. Workers use their configured coordinator address.

The existing owner routing still applies. Owners without a configured entry
use their existing authentication. A configured App that cannot authenticate
fails explicitly instead of falling back to another identity. Refresh failures
require checking credential health or starting a new session after a settings
change. A successful health check does not prove that the installation includes
a particular repository. Check the App's selected repositories if a PR tool
reports a repository access error.

Private-key rotation takes effect on the next token mint. Re-save the credential
to invalidate the cached token immediately, then start new sessions. To migrate
back to a PAT, edit the entry and choose **Personal access token**.

This feature adds no admin merge option and does not change repository rulesets.
Normal merge protections remain in force. Do not add the App as a bypass actor
merely to enable check-run reads.

See GitHub's [installation token documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)
and [check-run API permissions](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference).
